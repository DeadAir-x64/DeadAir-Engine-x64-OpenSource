# Авто-тесты Lua-скриптов

```bash
python xray-16/da_port/tests/run_tests.py
```

Каталог запуска значения не имеет — все пути считаются от самого файла. Возвращает ненулевой код при
любой провалившейся проверке, так что годится и для проверки перед коммитом.

Первый запуск собирает **LuaJIT** из `Externals/LuaJIT` (нужен `mingw32-make` из msys2, тот же, чем
собирается движок) и кладёт его в `tests/bin`, который не версионируется. Это принципиально: тесты
разбирают скрипты **той же версией 2.1.0-beta3, что линкуется в игру**, поэтому «разобралось здесь»
означает «разберётся в игре».

## Что проверяется

| проверка | что ловит |
|---|---|
| `hygiene` | удвоенный возврат каретки, BOM, смесь cp1251 и UTF-8 в одном файле |
| `engine` | вызовы `level.*`, которых нет среди биндингов порта |
| `options` | ключи `opt_*` из `atmosfear_options.ltx`, у которых нет ни одного читателя |
| `syntax` | разбор всех скриптов — и наших loose-правок, и полного набора мода |
| `globals` | **глобалы, которые читаются, но нигде не присваиваются** |
| `unit`-тесты | поведение конкретных функций на моках движка |

## Почему `globals` — главная проверка

Так выглядел реальный баг, стоивший половины дня: переменная `warn` читалась в трёх ветках
`surge_manager.script` и не присваивалась ни в одном из 378 скриптов. Все три ветки были мертвы —
радиопредупреждения о выбросе не играли **никогда, ни в одной сборке**. Lua на чтение
несуществующего глобала не ругается: он просто `nil`, а сравнение с ним тихо ложно. Ни запуск, ни
чтение кода глазами такое не ловят.

Проверка разбирает не текст, а **байт-код**: LuaJIT честно помечает обращения к глобалам опкодами
`GGET` и `GSET`, включая вложенные функции, поэтому ни комментарии, ни строки, ни динамика имён
результат не искажают. Убедиться, что проверка работает, можно за минуту: убрать присваивание `warn`
и запустить — `ПРОВАЛ globals: warn <- surge_manager.script`.

## Базовые линии

Три файла в `lint/` хранят то, что уже разобрано, чтобы тест ругался только на новое:

- `known_globals.txt` — движковые и стандартные символы (584 имени): `level`, `db`, `vector`, классы
  luabind и прочее, чему присваивания в скриптах не бывает по построению;
- `known_mod_bugs.txt` — **дефекты самого мода** с разбором каждого: опечатка `falout_manager` в
  сохранении актёра, `fasle` вместо `false`, `not_is_found`, несуществующая `if_then_else`. Набор
  остаётся зелёным, но при каждом запуске они печатаются справкой, чтобы не забылись;
- `known_dead_options.txt`, `known_missing_bindings.txt` — то же для настроек без читателя и для
  `level.actor()`, которого нет ни у автора, ни в базе Call of Chernobyl.

Дописывая имя в базовую линию, объясняйте рядом, почему это норма. Свалка без объяснений превращает
проверку в украшение.

## Unit-тесты

`unit/harness.lua` повторяет то, как скрипты грузит движок: у каждого файла своя таблица имён,
чтение проваливается в подставленную таблицу моков (`xrScriptEngine/script_engine.cpp:39`). Поэтому
скрипт можно загрузить целиком вне игры и дёргать его функции.

Покрыто то, что чинилось вслепую и может тихо развалиться обратно:

- `items_condition` — битовая маска поломок во всём диапазоне 0..31 и соблюдение `condition_avail`
  (на разрядности этой маски проект горел трижды);
- `surge_manager` — чтение настроек предупреждения и судьбы NPC, диспетчеризация `apply_fate`;
- `psi_storm_manager` — чтение судьбы NPC.

Мок движка намеренно минимальный: он покрывает ровно то, что нужно проверяемым функциям. Разрастаться
ему незачем — большая часть логики мода завязана на состояние мира, и её честнее проверять в игре.
